## 4. 自动 Discovery 排障：当前证据

### 4.1 本地修复与最新代码状态

Leader 侧已完成多轮 Discovery 接入： - 增加正式 mTLS Discovery
transport，使用 Leader `agent-cert.pem` /
`agent-key.pem`，使用可访问平台的系统 HTTPS 信任链。 - Resolver 增加
`expected_aic` 精确过滤和响应侧 AIC 校验。 - 正式三阶段入口增加
`--discover-partners`：先执行 mTLS Discovery，再将发现的 AIC 传入原有
Group 流程；发现失败时停止，不回退到显式
AIC，避免把自动发现失败伪装成成功。 - 离线测试曾通过 25 项；早期 mTLS
定向测试通过 4/4。 - 赵后续报告修复 mTLS transport 未保留系统 CA
的问题，最新修复 commit：`ecb256df`，报告 9 项测试通过。

修复后实际结果： - active 宽泛查询可返回约 40 个 ACS、50 个技能； -
两个公开 Agent 的精确查询及 alive 状态正常； - 三个正式 Agent 的精确
AIC + skill 查询仍全部为空； - 三个正式 Agent 的 `aliveMap` 无记录。

结论：本地 TLS/transport 问题进一步得到排除，但正式 Agent 的 Discovery
可见性问题仍然存在。注意：`ecb256df` 是赵报告的修复
commit；新对话仍需核实它所在分支、是否已合并/提交到最终交付分支，不要假设已经进入最终版本。

### 4.2 Registry 核对

通过官方 `agent list` 核对三个正式 Partner：

  条件                         Literature     Reader         Repository
  ---------------------------- -------------- -------------- --------------
  `acs IS NOT NULL`            是             是             是
  `aic IS NOT NULL`            是             是             是
  `is_active=true`             是             是             是
  `is_deleted=false`           是             是             是
  `approval_status=APPROVED`   是             是             是
  `visibility`                 `restricted`   `restricted`   `restricted`

队友阅读的开源 `discovery-server / registry-server` 实现显示，DSP
快照硬过滤条件为：

`acs IS NOT NULL AND aic IS NOT NULL AND is_active = true AND is_deleted = false`

本身不能证明对象已被 Discovery
收录；但三个对象均满足已知硬过滤条件。`visibility=restricted`
是明显差异，但可能是平台正常权限策略，不应直接称为 Bug。

### 4.4 严谨结论

**高置信度：** 阻塞集中在平台侧 Discovery
数据同步、索引或受限可见性查询环节。

**尚不能 100% 确定：** 1. DSP 实际快照是否包含三个正式 AIC； 2.
`visibility=restricted` 是否按平台设计阻止当前 Leader 身份发现； 3.
